Lines outside the file are moved to the nearest valid line instead of dropping the finding; whether the finding is right is for the self-check and the judge to decide.
- 2026-11-12: Retry layer for API errors: the chat model's own `max_retries=3` (Gemini), nothing else. When Part 4 adds a LangGraph `RetryPolicy` on the nodes, it must not retry API errors as well, or the attempts multiply. Ollama has no retry: a local connection error does not go away by waiting.
- 2026-11-12: `call_structured` returns `(parsed, raw_messages)` with one raw message per attempt, not a single raw message as in the plan. With a retry there are two LLM calls, and both have to be counted for the cost numbers. `StructuredOutputError` carries the raw messages for the same reason. `add_usage(stats, raw_messages)` does the counting.
- 2026-11-12: Checked on one Gemini call (`scripts/check_llm.py`, `gemini-3.8-flash`): `usage_metadata` was `input_tokens` 48, `output_tokens` 564, `output_token_details.reasoning` 447. So thinking tokens are included in `output_tokens` (117 visible + 447 thinking), and they were about 80% of the output here. Cost has to be computed from `output_tokens` as it is. Ollama (`qwen2.5-coder:7b`) reported 53 input and 95 output tokens for the same prompt.
- 2026-11-12: One rate limiter is shared by all Gemini models in the process (`get_rate_limiter` is cached), so reviewer and judge together stay under `REQUESTS_PER_MINUTE`.
- 2026-11-12: `review_baseline` never raises for a failed review. An unknown commit or a file the commit does not change is reported in `result.error` without an LLM call; an API failure and invalid output are reported there too, with the calls counted. Only a configuration error (missing key) is raised.
- 2026-11-12: `latency_s` is the wall-clock time of the whole review. It includes the waiting time of the rate limiter and the model's own retries, so the latency numbers of the evaluation have to say so, or the limiter wait has to be measured separately.
- 2026-11-12: Gemini requests have a timeout of 300 s (`API_TIMEOUT_SECONDS`). Without a timeout a request hung for more than five minutes. One review of a 298-line file took 110 s on `gemini-3.5-flash`, almost all of it thinking.
- 2026-11-12: The Gemini model is `gemini-3.5-flash` everywhere (default in `config.py`, `.env.example`, specification), not `gemini-3.8-flash` as in lab 3. Reason: 3.8 was overloaded (503/504) on 2026-11-09 and again on 2026-11-12, while 3.5 answered and honours temperature 0. Older entries in this file that name `gemini-3.8-flash` describe what was run at the time.
- 2026-11-12: Tool limits: `read_file` returns at most 200 lines per call and cuts lines after 1,000 characters; `search_code` returns at most 40 hits, each cut after 200 characters (the vendored minified JavaScript under `app/` has lines of many thousand characters); `list_files` returns at most 200 paths. Cut output always ends with a line that says so and what to do.
- 2026-11-12: `read_file` has `end_line: int = 0`, where 0 means "up to 200 lines from `start_line`" (the plan has `end_line = MAX_LINES`). With a fixed default of 200, a call with only `start_line=250` would be an invalid range.
- 2026-11-12: `is_readable` deny list (file name, in any folder): `.env`, `.env.*` except `.env.example`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`. Denied files are not read, not shown in search hits and not listed. Nothing in the target matches today.
- 2026-11-16: What counts as one of the 8 tool calls: every executed call, also when one model message asks for several, and every call to an unknown tool name. Without the second rule a model that keeps inventing names would never use up the budget, and only the recursion limit would stop it. Calls beyond the budget are answered with "Tool budget used up." and are not counted.
- 2026-11-16: `run_tools` checks the budget before the tool name, so an unknown name beyond the budget gets the refusal and is not counted. An unknown name within the budget is answered with a `ToolMessage` that lists the valid tool names.
- 2026-11-16: `run_tools` counts in a local variable. The state a node receives is a snapshot and is only updated after the node returns, so comparing `state["tool_calls_used"]` inside the loop would let every call of one message through. The node returns the new total, because `tool_calls_used` has no reducer and is overwritten.
- 2026-11-16: A trace entry is `{"tool_call_id", "tool_name", "tool_args", "status"}` with `status` one of `executed`, `unknown_tool`, `budget_exceeded`. The tool output is not in the trace: it is already in `messages`, and the traces are cached and published, so they stay small.
- 2026-11-16: `after_lookup` checks only whether the last message has tool calls, not the budget (the plan's diagram labels that edge "tool calls, budget left"). Reason: every tool call needs a matching `ToolMessage`, or the provider rejects the next model call, so a message with tool calls always has to pass through `run_tools`, which refuses what is over the budget. The budget is enforced in two places only: `run_tools` (what is executed) and `after_tools` (whether the loop continues). For the tests in 4.5 this means that "tool calls with the budget used" expects `"run_tools"` from `after_lookup`.
- 2026-11-16: Until `write_findings` exists (4.3), both conditional edges map the returned `"write_findings"` to `END` in their path map, so the routing functions do not change later.
- 2026-11-16: `write_findings` calls the plain model (not the one with the tools bound) with the whole conversation plus `FINAL_INSTRUCTION`, and passes the result through `clean_findings` with the text of the reviewed file, as the baseline does.
- 2026-11-16: The self-check (`verify_finding`) gets a fresh conversation: `VERIFICATION_SYSTEM_PROMPT`, then the rules, the finding and an excerpt of the file. It does not get the conversation that produced the finding, so it cannot agree with its own reasoning. The excerpt is the lines of the finding plus 20 lines before and after, clamped to the file, each with its real line number. 20 is a first value, to be checked on the dev units.
- 2026-11-16: When the excerpt is not enough to decide, the verifier answers `supported = false` and starts the reason with "Not enough context:". This follows the reviewer prompt (a wrong finding costs more than a missed one). The risk: a finding that rests on code the agent looked up in another file cannot be confirmed from 20 lines of the reviewed file and is dropped. The fixed prefix makes these cases countable in `dropped`; if there are many, this rule or the excerpt has to change.
- 2026-11-16: `AGENTS.md` stays in the prompt in full, for the reviewer and for the verifier. Measured at the increment commits: 11,239 characters at I1, 11,333 at I3, 11,647 at I8, 33 lines each, roughly 3,000 tokens (estimated at 4 characters per token). About half of it is about the Python code (the "Implementation" section, 5,431 characters at I3). Not trimmed, because the specification gives the baseline and the agent the same rules, the judge counts a broken `AGENTS.md` rule as a valid finding, and a `project-rule` finding cannot be verified without the rules. The cost: the look-up loop sends the conversation again on every `lookup` call, so with a used-up budget the rules alone are roughly 30,000 input tokens per unit. This goes into the cost comparison of the evaluation.
- 2026-11-16: `PROMPT_VERSION` is still "1": the reviewer prompt that the baseline checkpoint was measured with is unchanged, only the agent's prompts were added. It gets bumped when the agent prompts are final.
- 2026-11-16: The tools and the budget are not in `REVIEW_SYSTEM_PROMPT` but in a separate section, `LOOKUP_INSTRUCTIONS`, which only the agent appends (`build_agent_system_prompt(max_tool_calls)`). The baseline has no tools, and its prompt must stay the one its checkpoint was measured with. The section names the three tools, says when to look something up, that the changed file is already shown, the budget (unknown tool names count, calls beyond it are refused), and that the model should stop with one short sentence because the findings are asked for afterwards.
- 2026-11-16: The two state keys that break without their reducer are `checked` and `messages`; `trace` loses data without an error. ## The reviewed code is untrusted input (for the README architecture section)

The code under review is written by someone else (here: by AI agents), and a comment or string in it could tell the model to ignore its rules. The tools limit what such an injection can achieve: they can only read tracked files of one fixed commit, so the model cannot change or run anything, cannot leave the repository, cannot read files on the deny list, and cannot reach code from a later commit. The worst outcome is a wrong or missing finding in the report, which the self-check and the developer reading the report can still catch.

Tested in `tests/test_tools.py` on the fixture repository, without network or the cloned target: paths outside the repository, files from a later commit, the working tree, invalid regular expressions, bad line ranges, deny-listed files, output limits, and arguments that look like git options.
