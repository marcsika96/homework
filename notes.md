Lines outside the file are moved to the nearest valid line instead of dropping the finding; whether the finding is right is for the self-check and the judge to decide.

- 2026-11-12: `call_structured` returns `(parsed, raw_messages)` with one raw message per attempt, not a single raw message as in the plan. With a retry there are two LLM calls, and both have to be counted for the cost numbers. `StructuredOutputError` carries the raw messages for the same reason. `add_usage(stats, raw_messages)` does the counting.
- 2026-11-12: Checked on one Gemini call (`scripts/check_llm.py`, `gemini-3.8-flash`): `usage_metadata` was `input_tokens` 48, `output_tokens` 564, `output_token_details.reasoning` 447. So thinking tokens are included in `output_tokens` (117 visible + 447 thinking), and they were about 80% of the output here. Cost has to be computed from `output_tokens` as it is. Ollama (`qwen2.5-coder:7b`) reported 53 input and 95 output tokens for the same prompt.
- 2026-11-12: One rate limiter is shared by all Gemini models in the process (`get_rate_limiter` is cached), so reviewer and judge together stay under `REQUESTS_PER_MINUTE`.
- 2026-11-12: `review_baseline` never raises for a failed review. An unknown commit or a file the commit does not change is reported in `result.error` without an LLM call; an API failure and invalid output are reported there too, with the calls counted. Only a configuration error (missing key) is raised.
- 2026-11-12: `latency_s` is the wall-clock time of the whole review. It includes the waiting time of the rate limiter and the model's own retries, so the latency numbers of the evaluation have to say so, or the limiter wait has to be measured separately.
- 2026-11-12: Gemini requests have a timeout of 300 s (`API_TIMEOUT_SECONDS`). Without a timeout a request hung for more than five minutes. One review of a 298-line file took 110 s on `gemini-3.5-flash`, almost all of it thinking.
- 2026-11-12: The Gemini model is `gemini-3.5-flash` everywhere (default in `config.py`, `.env.example`, specification), not `gemini-3.8-flash` as in lab 3. Reason: 3.8 was overloaded (503/504) on 2026-11-09 and again on 2026-11-12, while 3.5 answered and honours temperature 0. Older entries in this file that name `gemini-3.8-flash` describe what was run at the time.
- 2026-11-12: Tool limits: `read_file` returns at most 200 lines per call and cuts lines after 1,000 characters; `search_code` returns at most 40 hits, each cut after 200 characters (the vendored minified JavaScript under `app/` has lines of many thousand characters); `list_files` returns at most 200 paths. Cut output always ends with a line that says so and what to do.
- 2026-11-12: `read_file` has `end_line: int = 0`, where 0 means "up to 200 lines from `start_line`" (the plan has `end_line = MAX_LINES`). With a fixed default of 200, a call with only `start_line=250` would be an invalid range.
- 2026-11-12: `is_readable` deny list (file name, in any folder): `.env`, `.env.*` except `.env.example`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`. Denied files are not read, not shown in search hits and not listed. Nothing in the target matches today.
- 2026-11-16: What counts as one of the 8 tool calls: every executed call, also when one model message asks for several, and every call to an unknown tool name. Without the second rule a model that keeps inventing names would never use up the budget, and only the recursion limit would stop it. Calls beyond the budget are answered with "Tool budget used up." and are not counted.
- 2026-11-16: `run_tools` checks the budget before the tool name, so an unknown name beyond the budget gets the refusal and is not counted. An unknown name within the budget is answered with a `ToolMessage` that lists the valid tool names.
- 2026-11-16: `run_tools` counts in a local variable. The state a node receives is a snapshot and is only updated after the node returns, so comparing `state["tool_calls_used"]` inside the loop would let every call of one message through. The node returns the new total, because `tool_calls_used` has no reducer and is overwritten.
- 2026-11-16: A trace entry is `{"tool_call_id", "tool_name", "tool_args", "status"}` with `status` one of `executed`, `unknown_tool`, `budget_exceeded`. The tool output is not in the trace: it is already in `messages`, and the traces are cached and published, so they stay small.
- 2026-11-16: `after_lookup` checks only whether the last message has tool calls, not the budget (the plan's diagram labels that edge "tool calls, budget left"). Reason: every tool call needs a matching `ToolMessage`, or the provider rejects the next model call, so a message with tool calls always has to pass through `run_tools`, which refuses what is over the budget. The budget is enforced in two places only: `run_tools` (what is executed) and `after_tools` (whether the loop continues). For the tests in 4.5 this means that "tool calls with the budget used" expects `"run_tools"` from `after_lookup`.
- 2026-11-16: Until `write_findings` exists (4.3), both conditional edges map the returned `"write_findings"` to `END` in their path map, so the routing functions do not change later.
- 2026-11-16: `write_findings` calls the plain model (not the one with the tools bound) with the whole conversation plus `FINAL_INSTRUCTION`, and passes the result through `clean_findings` with the text of the reviewed file, as the baseline does.
- 2026-11-16: The self-check (`verify_finding`) gets a fresh conversation: `VERIFICATION_SYSTEM_PROMPT`, then the rules, the finding and an excerpt of the file. It does not get the conversation that produced the finding, so it cannot agree with its own reasoning. The excerpt is the lines of the finding plus 20 lines before and after, clamped to the file, each with its real line number. 20 is a first value, to be checked on the dev units.
- 2026-11-16: When the excerpt is not enough to decide, the verifier answers `supported = false` and starts the reason with "Not enough context:". This follows the reviewer prompt (a wrong finding costs more than a missed one). The risk: a finding that rests on code the agent looked up in another file cannot be confirmed from 20 lines of the reviewed file and is dropped. The fixed prefix makes these cases countable in `dropped`; if there are many, this rule or the excerpt has to change.
- 2026-11-16: `AGENTS.md` stays in the prompt in full, for the reviewer and for the verifier. Measured at the increment commits: 11,239 characters at I1, 11,333 at I3, 11,647 at I8, 33 lines each, roughly 3,000 tokens (estimated at 4 characters per token). About half of it is about the Python code (the "Implementation" section, 5,431 characters at I3). Not trimmed, because the specification gives the baseline and the agent the same rules, the judge counts a broken `AGENTS.md` rule as a valid finding, and a `project-rule` finding cannot be verified without the rules. The cost: the look-up loop sends the conversation again on every `lookup` call, so with a used-up budget the rules alone are roughly 30,000 input tokens per unit. This goes into the cost comparison of the evaluation.
- 2026-11-16: `PROMPT_VERSION` is still "1": the reviewer prompt that the baseline checkpoint was measured with is unchanged, only the agent's prompts were added. It gets bumped when the agent prompts are final.
- 2026-11-16: The tools and the budget are not in `REVIEW_SYSTEM_PROMPT` but in a separate section, `LOOKUP_INSTRUCTIONS`, which only the agent appends (`build_agent_system_prompt(max_tool_calls)`). The baseline has no tools, and its prompt must stay the one its checkpoint was measured with. The section names the three tools, says when to look something up, that the changed file is already shown, the budget (unknown tool names count, calls beyond it are refused), and that the model should stop with one short sentence because the findings are asked for afterwards.
- 2026-11-16: The two state keys that break without their reducer are `checked` and `messages`; `trace` loses data without an error. Checked with a toy graph without a model. `checked`: two parallel `verify_finding` branches write to it in the same step, and without `operator.add` LangGraph raises `InvalidUpdateError: At key 'checked': Can receive only one value per step. Use an Annotated key to handle multiple values.` With a single finding there is one branch and nothing fails, so the error would only show on a unit with two or more findings. `messages`: without `add_messages` every node's return replaces the list, so after `lookup` the conversation is only the model's last answer; the system prompt, the diff and the earlier tool results are gone, and the next model call gets a conversation that starts with a tool call or a tool answer. No LangGraph error, the failure shows as a rejected or meaningless model call. `trace`: without `operator.add` only the entries of the last `run_tools` round are left.
- 2026-11-16: Retries, replacing the entry of 2026-11-12: the only retry layer is the LangGraph `RetryPolicy` on `lookup`, `write_findings` and `verify_finding` (4 attempts, 2 s first wait, factor 2). The Gemini model's own retries are off (`max_retries=0`), so the attempts do not multiply. LangGraph's default `retry_on` retries every exception except a list of built-in ones, which includes the daily quota, a wrong key and `StructuredOutputError`; `is_transient_error` in `llm.py` retries only a Gemini server error, a rate limit that is not the daily quota (the text `PerDay` in the message marks the daily one), and a timeout or lost connection.
- 2026-11-16: Usage is counted by my own callback, `UsageCallback`, passed in the config of the graph run. The plan names `UsageMetadataCallbackHandler`, but that one adds up tokens only and the evaluation needs the number of calls too. A failed call counts as a call, as in the baseline, so every retry attempt is counted.
- 2026-11-16: The recursion limit is `2 * max_tool_calls + 10` (26 for a budget of 8), not the fixed 40 of the plan: at most `max_tool_calls` rounds of two steps, plus the other nodes. The installed LangGraph has a default of 10,007 steps, so without this value there would be no safety net at all.
- 2026-11-16: `review_agent` never raises for a failed review, like `review_baseline`: an unknown commit or an unchanged file is reported in `result.error` without an LLM call, and so are an API failure after the retries, invalid output and a hit recursion limit. After a failure `findings` is empty, but `trace` and `stats` hold what happened up to the last finished step, because the graph is run with `stream_mode="values"` and the last state is kept. The self-check runs at most two branches at a time (`max_concurrency=2`).
- 2026-11-16: `docs/architecture.md` is written by `scripts/draw_graph.py` from the compiled graph, and a test fails when the file no longer matches the graph.
- 2026-11-16: The routing functions are defined inside `build_graph`, so a test cannot import them. `tests/test_graph.py` takes them from the compiled graph (`graph.builder.branches[node][name].path.func`) and calls them with small state dicts. This reaches into LangGraph's builder object, so it can break with a LangGraph update; the alternative would have been to move the functions to module level.
- 2026-11-16: The baseline retries a failed call by the same rule as the agent: up to 4 attempts, waiting 2 s, 4 s and 8 s, and only for errors `is_transient_error` accepts. The numbers are constants in `llm.py`, and a test checks that the `RetryPolicy` of the graph's model nodes has the same values, so the two systems of the evaluation cannot drift apart. The `RetryPolicy` line in `graph.py` uses the constants too. One difference remains: LangGraph adds a random wait of up to one second to each pause (jitter), the baseline does not. Every attempt is counted in `llm_calls` in both systems.
- 2026-11-16: The `review` command works in this order: open the repository, resolve the commit, list the files, and only then create the model. A wrong repository or commit therefore ends with one line and exit code 2 without an LLM call. Exit codes: 0 reviewed (or nothing to review), 2 wrong input or configuration, 3 at least one file could not be reviewed. The other files are still reviewed after a failure.
- 2026-11-16: `review` covers every changed file that `is_reviewable` accepts and that has at least one added line. The 15-line threshold of the evaluation units does not apply here. Files without added lines are skipped, which also covers deleted files: they have no new code, and the review would fail when it reads the file at the commit.
- 2026-11-16: `--verbose` does not use a second way of running the graph. `review_agent` got an optional `on_step(node, update)` function and streams with `stream_mode=["values", "updates"]`: the values keep the last state as before, the updates go to `on_step`. Until Exercise 5.2 the command prints a short summary per file and does not use `--out` yet.
- 2026-11-16: Reports: `review` writes `<out>/<sha7>/review.md` and `review.json` and prints the Markdown. The files are written before printing. The JSON is the list of `ReviewResult` objects through `model_dump()`, so it also holds the dropped findings and the trace; the Markdown shows only the number of dropped findings. A file is shown in one of three ways: a table of findings, "Reviewed, no findings.", or "**Not reviewed:**" with the error. The report sorts the findings itself (severity, then line), because the baseline does not sort them. The path of a file is taken from the unit id (the text after the first colon), since `ReviewResult` has no path field. Line breaks and `|` in model text are removed or escaped so they cannot break the table.
- 2026-11-16: Error cases of the `review` command and where each is handled. Not a repository, unknown or malformed commit: `GitError` from `gitrepo.py`, caught in `main`, exit 2. No reviewable Python: "Nothing to review", exit 0. Missing key or invalid setting: `ConfigError`, caught in `main`, exit 2. Ollama not running or model not pulled: `check_ollama` sends one request to the local server (`show`, not a model call) before the first file and raises `OllamaError`, exit 3; without this check every file would fail one after the other with the same connection error. API error, rate limit, invalid structured output: reported per file in `result.error`, the other files continue, exit 3. The first three kinds are answered before a model is created; the tests prove it with a model factory that fails the test when called.
- 2026-11-16: An error is shown on one line and cut after 300 characters on the screen and in `review.md` (a Gemini 429 error is many lines of JSON). `review.json` keeps the full text.
- 2026-11-16: Evaluation runs are stored one file per unit and system: `data/runs/<system>/<unit id with ":" and "/" as "_">.json`. A record is the `ReviewResult` plus `prompt_version`, `max_tool_calls` (agent only), `code_version` (the commit of this repository, with `-dirty` if `src/` has uncommitted changes) and a UTC timestamp. The model name is already in the result. The files are committed: they are the cached outputs that `reviewgraph eval --cached` reads without a key.
- 2026-11-16: Rerun rules, fixed before any evaluation run. (1) A unit whose file exists for the current model and `PROMPT_VERSION` is skipped. (2) A failed review (API error after the retries, invalid output, recursion limit) is stored with its `error`, counts as a unit without findings and is not repeated. (3) One exception: when the daily quota of the Gemini API is used up, the run stops and that unit is not stored, because no review took place; the next run starts with it. This is the same as an interrupted run, not a selective rerun: it is decided by the error type, before any result is seen. (4) A record of another model or prompt version is run again and replaced, so one evaluation never mixes two configurations. The old record stays in the Git history if it was committed.
- 2026-11-16: `reviewgraph eval` refuses a units file that contains test units unless `--test-set` is given, so the test set cannot be run by accident before the freeze. Its default is `data/units_dev.jsonl`. At this stage `eval` only runs the systems and prints how much is stored; the judge and the metrics are added in 6.2 and 6.5.
- 2026-11-16: The judge (`evaluation/judge.py`). It rates the medium and high findings of a stored run, high first, then reporting order, at most 3 per unit and system, as `valid`, `minor` or `invalid`, with the wording of the specification. It gets the rules, the finding, the rendered diff and the whole file with line numbers. `judge_finding` has no `system` argument, so the judge cannot see which system a finding is from. Rule for the unclear case: what the judge cannot confirm from what it is shown is `invalid`. A wrong category, severity or fix does not change the label.
- 2026-11-16: Verdicts are stored in `data/verdicts.jsonl`, one line per finding, appended and never rewritten. The key is `finding_id`: the first 12 characters of the SHA-1 of unit id, system, lines, category and explanation. A line also holds the finding, the judge model, `JUDGE_PROMPT_VERSION`, the tokens and a timestamp. The findings are judged in an order shuffled with a fixed seed (2026).
- 2026-11-16: Rules for the judge, fixed before any judging. (1) A finding with a verdict of the current judge model and judge prompt version is skipped. (2) A failed judgement (API error after the retries, invalid output) is not stored and is tried again on the next run. This differs from the reviews on purpose: a failed review is a result of the system under test, a failed judgement is a missing measurement. (3) The daily quota stops the judging. (4) After a change of the judge prompt the findings are judged again; the new line is appended and the later line counts. `JUDGE_PROMPT_VERSION` is separate from `PROMPT_VERSION`, because changing the judge does not change what the two systems produce.
- 2026-11-16: `reviewgraph eval --judge` only judges, it reviews nothing; plain `eval` only reviews. They are separate steps because of the order in 6.4: test run, hand labels, then the judge. The summary of `eval` shows how many selected findings have a verdict, but not the labels, so looking at the progress does not reveal the judge's verdicts before the hand check.

## The reviewed code is untrusted input (for the README architecture section)

The code under review is written by someone else (here: by AI agents), and a comment or string in it could tell the model to ignore its rules. The tools limit what such an injection can achieve: they can only read tracked files of one fixed commit, so the model cannot change or run anything, cannot leave the repository, cannot read files on the deny list, and cannot reach code from a later commit. The worst outcome is a wrong or missing finding in the report, which the self-check and the developer reading the report can still catch.

Tested in `tests/test_tools.py` on the fixture repository, without network or the cloned target: paths outside the repository, files from a later commit, the working tree, invalid regular expressions, bad line ranges, deny-listed files, output limits, and arguments that look like git options.
