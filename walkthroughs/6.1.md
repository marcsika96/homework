# Walkthrough 6.1: resumable runner with a cache

Written on 2026-11-16, right after the exercise.

## The idea

The evaluation is several hundred model requests, and you have 20 per day. So a run will be interrupted many times: by the quota, by Ctrl+C, by a closed laptop. The runner stores every unit the moment it is finished, and skips stored units on the next start. The stored files are also the "cached outputs" of the homework: with them the evaluation can be shown without a key.

## What was added

- [runner.py](../src/reviewgraph/evaluation/runner.py): the runner.
- [cli.py](../src/reviewgraph/cli.py): the `eval` command, in `run_eval`.
- [test_runner.py](../tests/test_runner.py): 11 offline tests.

How to call it, from the `homework` folder:

```
reviewgraph eval --limit 3                      both systems on the first three dev units
reviewgraph eval --system baseline              only the baseline, all dev units
reviewgraph eval --cached                       run nothing, show what is stored
reviewgraph eval --units data/units_test.jsonl --test-set      the test run, once, after the freeze
```

## The steps

Open `runner.py`. Read `run_units` first, then the small functions above it.

### Step 1: `run_units` is one loop with three exits per unit

For every unit:

1. **Already stored?** Then print "skipped" and go to the next unit.
2. **Review it** with `review_agent` or `review_baseline`, the same two functions as in the `review` command.
3. **Daily quota used up?** Then stop the whole run with `break`. Nothing is stored for this unit.
4. **Otherwise** build a `RunRecord`, save it, and count it.

It returns a small dict: how many were reviewed, how many skipped, and whether the quota stopped it.

### Step 2: one file per unit

`record_path` builds the name: `data/runs/<system>/<unit id>.json`. A unit id like `I5:app/studio/usecases/booking.py` has `:` and `/`, which cannot be in a file name, so `re.sub` replaces every unusual character with `_`.

Why one file per unit and not one big file: a big file would have to be rewritten after every unit, and a crash in that moment could destroy all earlier results.

### Step 3: `RunRecord` is the result plus where it came from

| Field | Why |
|-------|-----|
| `result` | The `ReviewResult`: findings, stats, error, model name |
| `prompt_version` | Which prompts produced it |
| `max_tool_calls` | The tool budget of the agent |
| `code_version` | The Git commit of this repository, with `-dirty` if `src/` has uncommitted changes |
| `timestamp` | When, in UTC |

With `code_version` and `timestamp` you can later show that the test runs were made with the frozen code, after the freeze.

### Step 4: `save_record` writes in two moves

It writes to `<name>.tmp` and then renames it to `<name>.json`. A rename happens in one step. So if the run is stopped in the middle of writing, there is a leftover `.tmp` file, but never a half `.json` file that looks like a finished unit.

### Step 5: `is_done` decides what "already stored" means

A unit is done if its file exists **and** was made with the current model and prompt version. Two consequences:

- A stored failure is done. Failed reviews are not repeated.
- A record of another model or prompt version is run again and replaced.

### Step 6: the daily quota is the one exception

`hit_daily_quota` looks for the text `PerDay` in the error (the same marker `llm.py` uses to decide not to retry). A normal failure means "the system tried this unit and failed", and that is a result. A used-up quota means "the system never got to try", and that is only an interruption. So the run stops, and tomorrow it starts with this unit.

### Step 7: the `eval` command in `cli.py`

`run_eval` has three steps:

1. Load the units, apply `--limit`, and refuse test units without `--test-set`.
2. Unless `--cached`: create the repository and the model once, and call `run_units` per system.
3. Print one summary line per system from the stored files.

Because step 2 is the only one that needs a key, `--cached` works without one.

Also new in `main`: `except KeyboardInterrupt` prints "Interrupted." instead of a traceback when you press Ctrl+C.

### Step 8: the tests

The most interesting one is `test_an_interrupted_run_continues_where_it_stopped`: the scripted model raises `KeyboardInterrupt` on the second unit, the test checks that one file exists, runs again and checks that one unit is skipped and one reviewed.

## Rules that are fixed now

They are in `notes.md` under Decisions, written before any evaluation run. That order matters: a rule made after seeing results could be bent to improve them.

1. A stored unit of the current model and prompt version is skipped.
2. A failed review is stored, counts as "no findings" and is not repeated.
3. A used-up daily quota stops the run and stores nothing for that unit.
4. A record of another model or prompt version is replaced.

## Things that differ from what you might expect

- `eval` does not compute any metric yet. It runs the systems and prints how much is stored. The judge (6.2) and the metrics (6.5) come later.
- The test set is protected by a flag: without `--test-set` a file with test units is refused.
- The baseline runs before the agent with `--system both`, because it needs one request per unit and finishes first.
- Unlike `review`, `eval` takes the repository from `TARGET_REPO_PATH` in `.env`, not from `--repo`.
