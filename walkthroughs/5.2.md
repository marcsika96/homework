# Walkthrough 5.2: Markdown and JSON reports

Written on 2026-11-16, right after the exercise.

## What was added

- [report.py](../src/reviewgraph/report.py): builds and writes the reports.
- [cli.py](../src/reviewgraph/cli.py): calls it at the end of `run_review`.
- [test_report.py](../tests/test_report.py): tests with hand-built results.

After a review there are two files in `<out>/<sha7>/` (by default `out/<sha7>/`):

| File | For whom | Content |
|------|----------|---------|
| `review.md` | A person | Header, one section per file, a footer with the costs |
| `review.json` | A program | Every `ReviewResult` in full, including the dropped findings and the trace |

The Markdown is also printed to the terminal.

## The steps

Open `report.py` and read it from the bottom to the top: the big function first, the small helpers last.

### Step 1: `write_reports` is the only function the command line calls

It builds the folder `<out>/<sha7>/`, writes `review.md`, writes `review.json`, and returns both paths and the Markdown text. `mkdir(parents=True, exist_ok=True)` means "create the missing folders, and do not complain if they exist".

### Step 2: the JSON is two lines

`result.model_dump()` turns a Pydantic object into plain dicts and lists. `json.dumps` turns those into text. Nothing is selected or renamed, so the file holds everything a `ReviewResult` has.

### Step 3: `render_markdown` builds a list of lines

The whole report is a Python list of strings, joined with `"\n"` at the end. It has three parts:

1. The header: commit, system, model, number of files.
2. One section per file, from `render_file`.
3. The footer: the stats of all files added up with `sum(...)`.

Building a list and joining it once is the usual way to write text with many lines. It is easier to read than one long string with `+=`.

### Step 4: `render_file` has three cases

A reader must be able to tell these apart, so each has its own wording:

| Case | What the report shows |
|------|-----------------------|
| The review failed | `**Not reviewed:**` and the error |
| Reviewed, nothing found | `Reviewed, no findings.` |
| Findings | A table, sorted from high to low severity, then by line |

If the self-check dropped findings, one more line gives their number.

### Step 5: the three small helpers

- `file_path` takes the path out of the unit id. The id is `"<commit>:<path>"`, and `split(":", 1)` cuts at the first colon only.
- `location` gives `path:12`, or `path:52-54` for a finding over several lines.
- `cell` makes model text safe for a table. A line break or a `|` inside a cell would break the table, so line breaks become spaces and `|` becomes `\|`.

### Step 6: the call in `cli.py`

Step 5 of `run_review` calls `write_reports` and then prints the Markdown and the two paths. The files are written before anything is printed, so they exist even if printing goes wrong.

One new line in `main`: `sys.stdout.reconfigure(errors="replace")`. The report contains text from the model. If the terminal cannot show a character, Python now prints `?` instead of stopping with an error.

### Step 7: the tests need no repository and no model

`test_report.py` builds `ReviewResult` objects by hand and checks the text. `render_markdown` only turns data into text, so it can be tested without anything else. This is why the rendering is its own function and not part of the command.

## Things that differ from what you might expect

- The report sorts the findings itself. The agent already sorts them in `finalize`, but the baseline does not.
- The Markdown shows only the number of dropped findings. The findings themselves are in `review.json`.
- If there is nothing to review, no report files are written.
- The per-file output during the run is now one progress line; the details are in the report at the end.
