# Walkthrough 6.2: the judge

Written on 2026-11-16, right after the exercise.

## The idea

To measure the two systems, somebody has to decide for every finding whether it is right. That is several hundred findings, too many to do by hand, so a model does it: the judge. It is a second, separate use of the LLM. The reviewer finds defects; the judge rates the reviewer's findings. You check 20 of its verdicts yourself in 6.4, to see whether the judge can be trusted.

## What was added

- [judge.py](../src/reviewgraph/evaluation/judge.py): the judge.
- [prompts.py](../src/reviewgraph/prompts.py): `JUDGE_SYSTEM_PROMPT`, `JUDGE_REQUEST`, `build_judge_request`.
- [cli.py](../src/reviewgraph/cli.py): the flag `--judge` of the `eval` command.
- [test_judge.py](../tests/test_judge.py): 11 offline tests.

How to call it, from the `homework` folder:

```
reviewgraph eval                 step 1: the systems review the units (6.1)
reviewgraph eval --judge         step 2: the judge rates the stored findings
reviewgraph eval --cached        show how much is stored and judged
```

## The steps

Open `judge.py`. The three functions of the plan come first, then the loop.

### Step 1: `select_for_judging` chooses what is judged

Not every finding goes to the judge: only medium and high ones, at most three per unit and system. The interesting line is the sort:

```python
chosen.sort(key=lambda finding: finding.severity != "high")
```

The key is `False` for high and `True` for medium, and `False` sorts first. Python's sort is "stable": items with the same key keep their order. So high comes first, and inside each group the reporting order stays.

### Step 2: `finding_id` gives every finding a name

A finding has no id of its own, so one is computed: the unit, the system, the lines, the category and the explanation are joined to one text, and `hashlib.sha1` turns it into a fixed string of letters and digits. The first 12 characters are the id.

Two properties matter:

- The same finding always gets the same id. That is what makes skipping possible.
- You cannot see from the id which system the finding is from. The hand-check sheet of 6.4 shows the id, and you must not know the system there.

### Step 3: `judge_finding` asks the model about one finding

It builds one message with four parts: the rules, the finding, the diff and the whole file with line numbers. Then it calls `call_structured` with the schema `JudgeVerdict`, the same helper the reviewers use.

Look at the arguments: there is no `system`. The function cannot tell the judge which system produced the finding, because it does not know. A rule that the code cannot break is better than a rule in a comment.

The loop around the call is the same retry rule as in the baseline: only errors that waiting can fix are tried again.

### Step 4: the prompt

`JUDGE_SYSTEM_PROMPT` in `prompts.py` defines the three labels with the wording of the specification:

| Label | Meaning | Counts as |
|-------|---------|-----------|
| `valid` | A real defect: wrong behaviour or a broken rule | A correct finding |
| `minor` | True, but cosmetic | Not counted |
| `invalid` | Wrong, or cannot be confirmed from what is shown | A false alarm |

Two decisions in it: what the judge cannot confirm is `invalid`, and a wrong category or severity does not change the label.

### Step 5: `verdicts.jsonl` is a file that only grows

`append_verdict` opens the file with mode `"a"` (append) and writes one line. Earlier lines are never changed, so a crash cannot damage them. `load_verdicts` reads all lines into a dict by id; if an id appears twice, the later line wins.

This is a different technique from 6.1 (one file per unit) for the same goal. Verdicts are small and there are hundreds, so one file with one line each is handier.

### Step 6: `judge_runs` is the loop

1. `findings_to_judge` collects the selected findings of all stored runs and shuffles them.
2. For each: already judged? Skip.
3. Otherwise call `judge_finding`. On a failure print it and go on; on a used-up quota stop.
4. Append the verdict.

The shuffle uses `random.Random(2026)`: a random generator with a fixed seed gives the same "random" order every time. Shuffling matters because the judge might change over a long run (a model update, or a prompt fix after the first hundred). Mixed order means both systems are affected equally.

### Step 7: the `--judge` flag

In `run_eval`, step 2 now has three branches: `--cached` does nothing, `--judge` calls `judge_runs`, and the default reviews. The summary got one more line per system: how many selected findings have a verdict.

## Rules that are fixed now

In `notes.md` under Decisions. The one that differs from 6.1:

- A failed **review** is stored and not repeated, because it is a result of the system being tested.
- A failed **judgement** is not stored and is tried again, because it is only a missing measurement.

## Things that differ from what you might expect

- The progress lines and the summary never show a label. In 6.4 you label 20 findings yourself before the judge runs on the test set, and nothing on the screen should tell you what the judge thinks.
- `judge_finding` returns the verdict and the raw model messages, not only the verdict as in the plan. The messages carry the token counts, which the cost numbers need.
- The judge has its own `JUDGE_PROMPT_VERSION`. Changing the judge prompt makes the findings be judged again, but it does not make the reviews run again.
