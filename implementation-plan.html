ReviewGraph Build Guide

A lab-style path from the specification to the homework pull request: eight parts, each split into exercises with a skeleton, the tasks, and a checkpoint that tells you when to move on.

Goal and structure

You build ReviewGraph, a command-line agent that reviews one commit of the dance-studio repository with a LangGraph graph (read context, look up code with at most 8 tool calls, write findings, double-check each finding), then evaluate it against a single-prompt baseline on the 37 frozen test units.

The parts follow the order in which things depend on each other. The estimates are rough; the rubric column shows where the points of the final submission come from.

Part 1 – Git access and review units

Everything the reviewer and the evaluation know about the target comes through one read-only class. This part also produces the dataset.

Exercise 1.1 – Read-only Git layer

Exercise 2.1 – Finding and result schemas

Category = Literal["authorization", "transaction", "model-rule", "validation",

    model: str

Exercise 2.3 – Prompts and the single-prompt baseline

Files: src/reviewgraph/prompts.py, src/reviewgraph/baseline.py

  • render_diff(repo, sha, path): present the change with the new-file line number in front of every line and a + marker on added lines. Models count lines in raw unified diffs badly, and your merge rule in Part 6 depends on line numbers.

  • REVIEW_SYSTEM_PROMPT: role, what counts as a defect (behaviour changes, rule violations), the category list, the severity scale, and the instruction to return an empty list when nothing is wrong. Keep the prompts in one module with a PROMPT_VERSION string that you bump on every change.

Part 4 – The LangGraph agent

The core of the homework and of the technical-depth points. The graph below is the specification of this part; your job is to wire it.

flowchart TD
    S([START]) --> LC[load_context]
    LC --> LU[lookup]
    LU -->|tool calls, budget left| RT[run_tools]
    LU -->|no tool calls| WF[write_findings]
    RT -->|budget left| LU
    RT -->|8 calls used| WF
    WF -->|one Send per finding| VF[verify_finding]
    WF -->|no findings| FI[finalize]
    VF --> FI
    FI --> E([END])

The four LangGraph abstractions you use, and where: a typed state with reducers (4.1), conditional edges that form a bounded loop (4.2), Send for a parallel fan-out with a reducer that collects the results (4.3), and per-node retry policies (4.4).

Exercise 4.4 – Retries, usage, and the diagram

  • Retries with backoff. Give the three LLM nodes a policy: g.add_node("lookup", lookup, retry_policy=RetryPolicy(max_attempts=4, initial_interval=2.0, backoff_factor=2.0)). Check in the documentation which exceptions the default policy retries and whether Gemini's rate-limit error is among them; pass retry_on= if not. Then switch off the chat model's own retries.
  • Recursion limit. Each loop round is two steps, so eight single-call rounds plus the other nodes come close to the default limit. Pass config={"recursion_limit": 40}; the tool budget is your real limit, this one is the safety net.
  • Usage. Collect tokens and call counts across all nodes with a callback in the config (look up UsageMetadataCallbackHandler in langchain_core.callbacks). tool_calls comes from tool_calls_used.
  • One entry function. review_agent(repo, sha, path) -> ReviewResult builds the graph, invokes it, measures wall-clock time and fills stats and trace. It has the same signature as review_baseline.
  • Diagram from code. Write graph.get_graph().draw_mermaid() into docs/architecture.md. A diagram generated from the compiled graph cannot drift from the implementation.

Part 6 – Evaluation

Fifteen points, and the part where order matters most: tune on dev, freeze, hand-label, then look at numbers.

Quota

One agent review can take up to 9 look-up calls, 1 findings call and one call per finding. Over 37 test units, plus the baseline, about 200 judge calls and all your dev-set tuning, that is well over a thousand requests. Look up the current daily request limit of your Gemini model in AI Studio before you plan the run days, and make every stage resumable.

Exercise 6.1 – Resumable runner with a cache

File: src/reviewgraph/evaluation/runner.py

  • run_units(units, system) writes one file per unit and system: data/runs/<system>/<unit-id-as-filename>.json. A unit whose file exists is skipped, so an interrupted run continues where it stopped.
  • Each record holds the ReviewResult plus provenance: model id, PROMPT_VERSION, the Git commit of the homework repo, and a timestamp. With this you can show that the test runs were made after the freeze.
  • A failed review is stored with its error and counted as a unit without findings. Do not rerun failures selectively after you have seen results; rerun rules belong in notes.md before the test run.
  • These files are the cached outputs of objective 4. reviewgraph eval --cached must work from them without a key.

Checkpoint

Run both systems on three dev units, interrupt the second run with Ctrl+C and start it again: finished units are skipped.
